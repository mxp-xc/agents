# 工程与代码规范

本文件由全局指令按需引用，在编写或修改业务代码、测试、错误处理、日志、API schema 或提交前自检时遵循。

## 代码组织与摘要

- 内部私有辅助逻辑在少量代码时不提前拆文件；只用一次且不提升可读性或可维护性的包装函数直接内联，保留便于调试的关键中间变量。
- 架构分层、对外契约、领域模型与边界接口按项目架构约定独立组织，不因初期代码量少而合并展平。
- 仅在业务、协议或用户明确要求时计算内容 hash、SHA 等摘要。

## 测试

- 测试覆盖业务行为、关键分支、边界、错误处理和对外契约；除产品契约、审计或排障需要外，不测内部实现细节。
- 日志框架、配置、上下文注入、轮转和保留策略可单独测试；业务测试只验证业务结果、状态和异常契约，不断言 `logger.xxx` 调用、日志文案、级别或附带的异常信息。

## 错误处理与日志

- 异常捕获后继续向上抛出时，当前层记录有排障价值的业务上下文日志；错误对象和堆栈由最终消费异常的一层统一记录，当前层不重复记堆栈。
- 异常在当前层被消费（降级、转为返回值或不再外抛）时，记录完整错误对象和堆栈（如 `logger.error({ err }, msg)`），不静默忽略、不只记 `err.message`，也不为拿堆栈而自抛自捕。
- 识别关键路径（核心决策、外部调用、数据写入、状态流转）并加运行时日志：同一请求用 `trace_id` 串联，记录输入、关键中间值和外部响应，使一次用户操作可复现。
- 敏感资源（资产、权限、配置、用户等）的增删改和授权等关键操作写只读审计日志入库，记录操作人、时间、对象、变更前后值和结果。

## 代码注释与 API 字段说明

- 新增源码文件在开头简述职责与使用约定；新增类、公共函数或方法在定义处用注释或 docstring 说明职责与调用约定；新增枚举成员在旁注明取值、业务含义及与其他成员的区别。
- 新增或修改 API 请求、响应字段的业务语义时，在定义处说明用途，按需写明允许值、默认值、省略或传空时的行为及必填/生效条件；Pydantic schema 优先用 `Field(description=...)` 写入 OpenAPI。
- 提交前对照 diff，检查本次涉及的上述代码与接口元素是否已补齐说明。
