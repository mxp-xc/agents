# 代码检查

检查用户指定的代码，验证疑似问题并报告可操作的 findings。默认只检查；
仅当用户明确要求修复时修改代码。

## 范围

- 接受用户指定的任意文件、目录、模块、功能或仓库。
- 不要求提供 Git diff、commit、branch 或 pull request。
- 覆盖所有相关的问题领域，包括：
  - 正确性与对外契约
  - 安全与信任边界
  - 性能、并发与资源管理
  - 错误处理、降级行为、日志与可观测性
  - 代码质量、结构与可维护性
  - 依赖选型与平台惯例
  - 测试与验证缺口

这些领域的详细检查规则后续单独补充。尚未定义规则目录时，不要自行虚构固定的
检查清单。

## 工作流

1. 确定检查目标并读取适用的项目规范。
2. 阅读足够的关联代码和契约，在实际上下文中判断目标代码。
3. 将适用的问题领域划分为有意义的检查块。
4. 存在可用 subagent 时，将每个主要检查块分配给独立的 reviewer subagent。
   reviewer 只检查并返回候选 findings，不修改代码。
5. 验证前合并重复或根因重叠的候选 findings。
6. 将候选 findings 交给新的 verifier subagent。要求 verifier 检查相关代码、
   主动尝试反驳每项判断，并将其分类为 `CONFIRMED`、`PLAUSIBLE` 或
   `REFUTED`。
7. 报告经过验证的结果。从 findings 中排除 `REFUTED`，并明确
   `PLAUSIBLE` 中尚未消除的不确定性。
8. 仅当用户明确要求修复时修改代码，并在修改后验证行为。

## Finding 要求

- 每条 finding 必须关联具体位置和可观察证据。
- 说明问题的触发条件和实际影响。
- 区分已经验证的缺陷与仍有不确定性的风险。
- 除非违反适用的项目规范或造成具体的维护风险，否则不要把风格偏好报告为缺陷。
- 将 reviewer 的输出视为待验证假设，而不是事实。
