# 一次性迁移

**迁移是一次性运维动作，不是代码。** 代码里只存在当前最终形态；版本迁移函数、迁移映射、读取时惰性升级、兼容 shim 都属于历史包袱，一律不进仓库。

## 步骤

1. **代码直接改到最终形态**——schema/模型/契约定型为目标样子；不为兼容旧形态引入版本号步骤、迁移链或升级分支。
   完成标准：diff 里除最终形态外，不存在任何"从旧形态升级到新形态"的代码路径。

2. **存量数据用一次性脚本刷库**——脚本放 `temp/code/`（gitignored），幂等、带 `--dry-run`；只注入缺失字段、不覆盖已有合法值，脏版本号一并归一。
   完成标准：dry-run 列出全部待改记录；实跑后复跑 dry-run 为零。

3. **对本环境立即执行，其余环境写部署注意**——开发库当场刷；生产及其他环境在对应任务单/PR 正文写明"部署时需对数据存储执行一次迁移脚本，未刷库的存量数据会回退/重置"。
   完成标准：任务单/PR 正文包含部署注意。

4. **脚本用完即弃**——可以留在 temp/ 备查，但绝不 `git add`；提交前确认暂存区与仓库无 temp/ 脚本。
   完成标准：`git status`/暂存区不出现该脚本。

## 为什么

- 版本化迁移代码是打补丁：正常开发的完整功能没有 v1/v2 之说；每多一条迁移链，读取路径就永久背着一段只为历史数据存在、新数据永远不走的逻辑。
- 持久 schema 切换由部署一次性完成，应用代码不做自动迁移。
- 漏刷库的代价（该数据回退/重置）由部署步骤兜底并在任务单写明，不靠代码兼容消化。
