# 项目结构指导

按技术栈组织项目目录。空项目给出可运行的初始骨架；已有项目给出最小改动的调整方案。范围限于目录结构、文件职责和模块边界。

## 适用场景

- 空项目：技术栈已定，或需要推荐。
- 已有项目：目录混乱、依赖越界，或新代码不知道放哪。
- 只问一个模块放哪：读对应参考文件直接回答。

## 工作流

1. **收集输入**。确认起点、技术栈、规模和预期变化（异步任务、多入口、前端、独立服务）。
   已有项目先读现状：入口、包结构、配置、测试、构建方式；沿 import 弄清依赖方向，记录重复目录、越界引用和没有归属的文件。
   完成标准：说清用哪些框架、规模多大；问题位置有文件证据。
2. **确定技术栈**。用户未指定时，ls references/ 读 [index.md](references/index.md)，按目标语言进子目录读 picks.md，给出推荐组合和理由，等用户确认。
   完成标准：框架清单确定，用户认可。
3. **读取对应参考**。ls references/，按语言进子目录，文件名即框架；语言无关的规范（如 ddd.md）在根目录。按用到的框架逐个读；组合型文件（如 fastapi.md）开头列出的相关文件一并读。没有对应文件的框架按通用原则组织，理由写进方案。
   完成标准：用到的参考文件全部读过，方案规则有出处。
4. **输出方案**。
   - 空项目：目录树加每目录一句职责；最小可运行文件集（pyproject.toml、入口、配置、一个贯穿各层的示例资源、一个冒烟测试）。示例资源用业务名词（orders），不用 demo、sample。
   - 已有项目：先列问题和证据，再给目录树、迁移步骤和风险点。只移动文件、改 import 就够的，不加深拆分；改动大时按模块分批，每批之后保持可运行。
   完成标准：方案含目录树、理由和迁移顺序；未确认前不动文件。
5. **落地并验证**。用户确认后创建、移动或删除文件；结构变更与业务改动分开，移动用 git mv。验证：依赖方向符合布局，import 全部可解析，测试通过，入口可启动；空项目跑通最小请求，已有项目逐批复跑测试。
   完成标准：验证全部通过，未通过项有归属和修复动作。

## 通用原则

- 结构匹配规模。脚本不建包；小型应用三层（入口、业务、数据访问）；多入口、多团队或需要替换的基础设施出现时，再引入领域分层。
- 依赖单向向下。入口引用业务，业务引用数据访问和外部系统接口；判断标准是 import 方向，下层不 import 上层。
- 按业务划分，按层放文件。目录和文件名用领域词；同一业务的 model、schema、service 分属各层目录。utils、common、misc 只放真正跨业务的代码。
- 公共配置在一个入口装配。数据库连接、环境变量、日志在启动模块集中创建，其余模块经参数或依赖注入取得。
- 测试镜像源码。tests/ 路径与源码包对应，模块迁移时测试跟着走。
- 从最小可用结构开始。出现真实边界（独立生命周期、独立团队、明确替换需求）才加目录。

## 约束

- 只建议和修改结构；与结构无关的代码保持原样。
- 技术栈由用户决定，本 skill 只给推荐和理由；拆分以当前规模为上限。
- 工具按用户项目现状选择；新项目默认 uv + pyproject.toml，用户环境另有约定时以用户为准。
- 引用只落在本 skill 目录内。
