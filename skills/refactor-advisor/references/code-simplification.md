# 代码简化

检查保持行为不变的精简机会，关注控制流、冗余状态，以及读懂和修改同一行为所需的追踪成本。

## 检查重点

- 查找深层嵌套、复杂条件和嵌套三元表达式，判断提前返回、局部命名函数或关键中间变量是否能理清逻辑。
- 检查复杂回调链是否适合用 `async` / `await` 表达，保留原有异常处理和执行时序。
- 追踪值的来源、写入与读取，查找只写不读、可直接推导却反复同步的状态，以及没有业务意义的中间转换。即使当前同步正确，也要判断每次改规则是否都要核对多处赋值。
- 查找晦涩命名、冗长表达式和表达同一规则的局部重复代码。使用有业务含义的名称；拆开长链或使用解构，以更容易理解为准。
- 检查不可达代码、无用导入、废弃分支、注释掉的实现和遗留调试输出。区分调试输出与有用途的业务日志。
- 检查透传 helper、多余间接层，以及让读写路径反复跨函数或文件跳转的抽象。沿一次具体行为说明哪些跳转没有隐藏规则或减少调用方负担。

## 判断边界

认定代码无用前，结合使用方式核对调用方、对外导出、动态注册、配置引用及加载副作用等间接用途。搜索不到直接调用，只能作为排查线索。

简化建议应说明行为等价的依据，按改动核对返回值、异常、求值与副作用顺序、异步时序、资源释放或对外契约；无法排除差异时，写明证据缺口。

以可读性和维护收益判断，保留项目风格。行数减少、调用次数少或个人语法偏好本身不足以构成问题；有调试价值的中间变量、隐藏复杂度或提供有效测试边界的抽象仍有价值。

说明精简后少维护了哪些状态、分支或跳转。成本已在局部消除、行为能直接读清时即可停止；为了缩短代码而压成更难读的表达式，或把被封装的规则散到调用处，都可能抵消收益。

## 判断示例

- 场景：同一文件中的多个私有 helper 逐层转发相同参数，没有转换、校验或其他用途；读完调用链才发现最终只是读取一个字段。判断：可报告冗余间接层，建议合并到有业务含义的调用处，减少理解这次读取的跳转。先确认这些 helper 没有导出、动态引用或独立契约。
- 场景：`items` 每次增删后都会重新赋值 `isEmpty`，两者始终同步且测试全绿；所有读取点只需要判断当前数组是否为空。判断：可报告冗余状态，直接由 `items.length` 推导后，增删路径无需再维护第二份状态。核对没有外部写入、历史快照或更新通知契约后，删除同步赋值即可。
- 场景：处理函数没有直接调用点，但配置中的名称会在启动时解析并注册该函数。判断：不报告为死代码，配置和注册过程就是使用证据。
- 场景：把两个依次执行的 `await` 改成 `Promise.all`，代码更短，但后一个操作依赖前一个操作的副作用。判断：不作为等价简化建议，执行顺序已经改变。
