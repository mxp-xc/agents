# 代码简化

检查保持行为不变的精简机会，关注控制流、冗余状态、无用代码和间接层带来的理解成本。

## 检查重点

- 查找深层嵌套、复杂条件和嵌套三元表达式，判断提前返回、局部命名函数或关键中间变量是否能理清逻辑。
- 检查复杂回调链是否适合用 `async` / `await` 表达，保留原有异常处理和执行时序。
- 查找重复计算、重复维护的状态、晦涩命名、冗长表达式和表达同一规则的局部重复代码。使用有业务含义的名称；拆开长链或使用解构，以更容易理解为准。
- 检查不可达代码、无用导入、废弃分支、注释掉的实现和遗留调试输出。区分调试输出与有用途的业务日志。
- 检查透传 helper、多余间接层，以及让理解同一行为必须反复跳转的抽象。

## 判断边界

认定代码无用前，结合使用方式核对调用方、对外导出、动态注册、配置引用及加载副作用等间接用途。搜索不到直接调用，只能作为排查线索。

简化建议应说明行为等价的依据，按改动核对返回值、异常、求值与副作用顺序、异步时序、资源释放或对外契约；无法排除差异时，写明证据缺口。

以可读性和维护收益判断，保留项目风格。行数减少、调用次数少或个人语法偏好本身不足以构成问题；隐藏复杂度或提供有效测试边界的抽象仍有价值。

## 判断示例

- 场景：同一文件中的多个私有 helper 逐层转发相同参数，没有转换、校验或其他用途；读完调用链才发现最终只是读取一个字段。判断：可报告冗余间接层，建议在调用处直接读取。先确认这些 helper 没有导出、动态引用或独立契约。
- 场景：处理函数没有直接调用点，但配置中的名称会在启动时解析并注册该函数。判断：不报告为死代码，配置和注册过程就是使用证据。
- 场景：把两个依次执行的 `await` 改成 `Promise.all`，代码更短，但后一个操作依赖前一个操作的副作用。判断：不作为等价简化建议，执行顺序已经改变。
