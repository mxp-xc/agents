# 性能与数据访问

结合实际数据规模、调用频率、复杂度和已有测量，检查计算、IO 与内存成本是否值得通过重构降低。

## 检查重点

- 沿一次请求或任务统计数据访问次数，检查重复 IO、N+1、循环内重复扫描或计算。核对 ORM 的延迟加载、预加载和请求内复用，确认表面上的调用是否实际触发外部访问。
- 核对查询范围、返回字段、分页与批次上限。检查只需计数或少量结果却加载全部数据、先全量加载再分批，以及多轮处理持续保留中间结果的情况。结合记录大小和保留时长判断内存成本。
- 检查并发数和排队量是否受控，是否随输入规模直接增长，是否超过连接池、下游限流或任务容量。串行 `await` 也可能承担顺序、事务或限流要求，不能只为缩短等待时间改成并发。
- 结合执行位置检查同步 IO 和重计算：请求线程或事件循环中的阻塞，与启动时处理少量配置的影响不同。用已有 trace、profile、查询计划、监控或基准结果定位耗时，核对测量的输入规模和运行条件。
- 评估批量处理和缓存能否消除实际重复工作。批次大小需考虑查询参数、响应体和事务范围；缓存需核对复用机会、键空间、容量、失效方式、数据新鲜度与租户隔离，避免用额外状态掩盖无效查询。

## 判断边界

把输入规模、调用频率和成本增长联系起来。代码可以证明每条记录新增一次查询、无上限地并发请求或持续积累数据时，可以报告增长风险，无需先做 benchmark；这只能证明成本如何增长，不能据此宣称当前已成为瓶颈、必然耗尽资源或能提速多少。若瓶颈判断依赖尚无的测量，指出需要验证的具体路径和指标。

循环、`await`、全量读取或没有缓存本身不构成问题。核对实际规模、入口限制、调用次数和已有测量；数据量小且有稳定上限、成本满足要求，或收益不足以覆盖复杂度时，可以保持现状。

先减少不需要的数据、重复访问和重复计算，再评估批处理、并发、缓存或算法调整；不默认引入缓存、并发或新库。建议需保持相关契约，包括结果顺序、缺失项、部分失败、事务一致性、下游限流和取消行为。若优化依赖改变契约，明确指出这一前提。

使用已有测量或提出验证方案，针对候选的成本来源比较相同规模下的查询次数、峰值内存或耗时，并核对行为契约。

## 判断示例

- 场景：列表先查询订单，再为每个订单查询客户；代码和 ORM 配置确认每次都访问数据库，列表允许返回数百条。判断：可报告 N+1 的增长风险，评估按客户 ID 去重后批量查询。依据：N 条订单产生 `1 + N` 次查询；无需先证明延迟超标，但没有测量不能声称具体提速。批量结果仍需按订单顺序组装，并保持客户缺失时的行为。
- 场景：导出读取全部历史记录到数组，再按 500 条切块写入文件；记录持续增长，数组直到导出结束才释放。判断：可报告内存随总记录数增长的风险，评估从数据源分页或流式读取。依据：写出批次没有限制读取侧的常驻数据量；这还不能证明当前已发生内存不足。分批读取需核对稳定排序和导出期间的一致性要求。
- 场景：任务最多处理 8 项，依次 `await` 调用下游；下游要求逐项完成后再提交下一项，已有同规模测量满足任务时限，各项数据也不复用。判断：保持现状，不因循环内 `await` 或没有缓存而报告问题。依据：规模有界，串行执行承担明确顺序契约，尚无增加并发或缓存的收益证据。
