# 数据与契约

检查同一业务概念在输入、API、领域模型和存储之间的含义是否一致，关注转换、边界校验和契约演进是否容易发生偏差。

## 检查重点

- 沿数据的写入、读取和输出核对字段含义及表示约定，包括单位、精度与舍入、时区、枚举值，以及缺失、`null`、空值和默认值的区别。名称或类型相同不能证明含义相同，表示不同也可能是明确的边界设计。
- 阅读模型声明、接口契约、序列化与反序列化代码，核对转换是否保留业务需要的信息。关注隐式类型转换、精度损失、枚举兜底和默认值填充是否掩盖了调用方需要区分的状态。
- 检查同一转换或校验规则是否散落在多个入口，造成同步修改容易遗漏或已有差异；也检查层间各自假定对方已经校验的缺口。区分输入格式、业务约束与存储约束，按各边界承担的契约判断重复校验是否必要。
- 评估字段增删、类型调整或含义变化时，哪些调用方、序列化过程和契约测试需要一起调整。结合实际读取路径检查已有数据能否被正确解释；只改类型声明或 schema，不能证明契约已经一致。

## 判断边界

内部模型、外部 DTO 和存储结构可以独立设计。判断依据是映射是否明确、语义是否保留、修改是否容易遗漏；不要求全项目使用同一份 schema、统一 DTO、自动生成代码或通用 mapper。多处出现相似字段本身不构成问题。

建议应明确哪一边定义契约、哪里负责转换与校验，以及按契约需要验证的输入、输出和往返转换。对已有偏差，区分当前可触发的错误与契约变更时的维护风险。涉及数据调整时，说明既有数据和部署顺序的影响及待核实约束；根据真实调用方和部署约束评估方案，兼容层或版本链不作为通用修复手段。

安全审计不属于本领域的主要检查目标。

## 判断示例

- 场景：支付 API 用整数分表示金额，批量导入用元的字符串表示。两个入口分别转换为领域金额，一个四舍五入，另一个直接截断；同一笔金额经两条路径得到不同结果。判断：应报告转换规则漂移。依据：两条路径表达同一金额契约，却在边界值上产生不同结果；应核对规则归属及两个入口的金额测试。
- 场景：PATCH 契约规定缺失字段表示保持原值，`null` 表示清空；反序列化时把两者都填成 `null`，更新层据此清空字段。判断：应报告缺失值语义丢失。依据：转换消除了调用方需要表达的区别；调整时需检查调用方、序列化过程和部分更新的契约测试。
- 场景：API 返回带时区的时间字符串，领域使用时间对象，数据库保存 UTC 时间；边界转换明确，测试覆盖跨时区输入与输出。判断：不因存在三种表示而报告。依据：表示各自适配边界，转换保留同一时刻，现有证据未显示语义漂移或同步维护缺口。
