# 依赖与重构

检查是否值得建立共享接口、封装复杂度或调整第三方依赖，权衡收益、改动成本和行为风险。先理解当前行为、调用方和已有依赖，区分项目特有规则与通用技术问题。

## 抽取与封装

- 抽取函数、组件、模块或 adapter 时，核对是否集中真实复杂度、缩小调用接口，或让规则调整更集中。列出调用方当前承担的协议知识、顺序约束和错误处理，说明封装后哪些责任由内部承担。
- 判断重复代码是否表达同一规则、是否一起变化，结合当前需求或近期修改核对同步维护的位置。多调用方是收益证据之一，单调用方的有效封装也可有价值。
- 用删除测试辅助评估已有抽象：去掉它后，调用方要重新承担哪些细节？隐藏真实复杂度是保留依据；若只是透传，比较内联后是否更易理解，核对其是否承担稳定契约或项目约束。
- 好的抽取隐藏 IO、框架、协议、解析或存储细节，减少入口中的重复编排，提供自然的测试边界。若只是换个名字包装一次调用、为假设中的替换增加接口，或让测试依赖更多实现细节，应重新评估收益。
- 项目特有规则优先用项目语言表达。提取后若调用方仍需了解同样的细节，或理解一个概念要跨更多文件跳转，说明抽取尚未改善维护。

## 第三方依赖

先检查现有依赖是否已经解决问题。对复杂的通用问题或标准协议，再评估引入或替换库；简单本地逻辑和低优先级功能通常不值得承担迁移成本。

提出具体包的引入、替换或升级建议前，使用包管理器或 registry 元数据、官方文档和项目用法查验当前证据，不凭记忆断言维护状态或 API。按项目约束评估：

- 维护与社区是否足以支持项目风险，API 是否稳定且有文档，许可证是否适用。
- 能否减少项目代码或提高可靠性，迁移收益是否值得成本。
- 安全、体积、原生构建和运行环境是否适配；对不确定项说明证据缺口。
- 依赖细节是否散布到业务代码，是否值得用模块、adapter、hook 或组件集中隔离；封装应隐藏复杂度，避免无价值透传。

可选结论包括保留、引入、替换、隔离依赖、提取本地模块或暂不重构。当前方案够用、迁移主要制造改动，或关键约束尚不清楚时，可保留现状或暂缓建议。

## 判断边界

用同一个实际场景比较现状与建议方案：调用方少理解哪些细节，同一规则少维护哪些位置，需要增加哪些接口、测试和迁移工作。建议可止于局部函数或现有模块内的封装；无需预先完成选型或全项目重构方案。

表面相似但独立变化的业务行为应分别保留。包的流行程度、较新版本或代码量减少，本身不足以构成问题。

## 判断示例

- 场景：三个任务入口都正确处理同一供应商的游标分页、重试和错误转换，近期调整重试策略时逐处修改。判断：可报告公共抽取机会。集中后入口只消费业务结果，协议策略及相关验证在一处维护；核对分页终止、重试上限和错误语义，计入三个入口的接入成本。
- 场景：上传封装只有一个调用方，内部处理分片协议、恢复位置和失败清理，对外只接收文件并返回上传结果。判断：保留该封装。删除后调用方要重新承担协议及清理细节，单调用方数量不足以支持内联。
- 场景：优惠券与会员折扣的计算代码相似，但需求规定两套规则独立变化。判断：不因代码相似就建议合并，公共函数可能迫使调用方传入更多业务分支。
- 场景：现有库已满足需求，只因另一个框架更流行就建议迁移。判断：不形成 finding；还缺少现有方案的具体不足、迁移收益和当前依赖证据。
