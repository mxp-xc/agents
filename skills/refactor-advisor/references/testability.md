# 可测试性

检查业务行为能否以合理代价稳定验证，关注测试条件能否控制、关键分支能否触发，以及结果能否从业务边界观察。结合目标代码、已有测试和测试设施判断验证成本。

## 检查重点

- 检查隐式的时间、随机数、环境变量、单例和进程级可变状态依赖。核对测试能否稳定设置边界条件、隔离不同用例并恢复环境，关注只能靠等待、反复运行或固定执行顺序验证的行为。
- 检查业务规则与网络、数据库、文件等外部 IO 混杂后，是否必须启动无关服务或产生真实副作用才能验证一条规则，是否难以构造失败、超时等关键路径。结合现有替代实现、临时资源和集成测试设施，判断是否缺少有效的测试边界。
- 检查测试是否过多绑定私有方法、内部字段、非契约性的调用顺序或中间数据形状。关注行为未变的内部调整频繁导致测试失败，以及内部调用断言通过却无法证明业务结果的情况。
- 核对测试能否验证业务结果、状态变化、异常和对外契约。交互断言应对应真实契约，例如支付请求金额或禁止重复扣款。

## 判断边界

覆盖率、mock 数量、没有单元测试或使用真实数据库，本身不足以说明设计难以测试。重点说明哪项业务行为难以稳定验证、当前准备或维护成本来自哪里；单纯缺少测试应与妨碍验证的代码设计分开判断。

调整以降低具体的验证成本为准。可控参数、现有测试设施或局部边界可能已经足够，不默认要求所有逻辑变成纯函数、所有依赖建立注入接口。能稳定覆盖事务、协议或持久化契约且运行成本可接受的集成测试，可以保留。

## 判断示例

- 场景：优惠资格在函数内部读取当前时间和共享活动配置；测试靠等待到期并按固定顺序修改配置，单独运行通过、并行运行偶发失败。判断：可报告条件不可控与用例隔离问题。时间边界无法直接设定，共享配置会互相干扰；可评估允许传入判定时间、隔离配置等局部调整，验证到期前后结果。
- 场景：退款测试只断言三个私有 helper 的调用顺序和一条日志，未检查退款金额与最终订单状态；合并 helper 后测试失败，金额算错时测试仍通过。判断：可报告测试绑定内部细节且未验证业务结果。应围绕退款金额、状态和异常契约断言；若调用顺序承担外部协议约束，则保留对应契约验证。
- 场景：订单持久化使用临时数据库和事务回滚，测试通过公开入口验证唯一约束、提交与回滚结果，数据彼此隔离，运行成本符合项目要求。判断：不因依赖真实数据库或缺少逐层 mock 建议重构。这些测试直接验证存储契约，现有设施已提供稳定边界。
