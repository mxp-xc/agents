# 依赖与重构

检查重复逻辑能否集中、复杂步骤能否藏在一个好用的接口后面，以及自写代码是否值得换成语言内置能力或第三方库。先看当前用法和已有依赖，再比较少维护了什么、接入要改什么、行为是否会变。

## 抽取与封装

- 抽取函数、组件、模块或 adapter 时，列出调用方现在必须处理的翻页、重试、解析、清理等步骤，说明哪些能交给内部完成，调用后还能拿到什么结果。
- 结合近期修改，核对相似代码是否总要一起改。多个调用方可以支持抽取，只有一个调用方也可能需要封装复杂步骤。
- 试想删掉一个已有封装：调用方是否要重新处理协议、顺序和错误？若会，封装有价值；若只是换个名字转发参数，比较直接调用是否更清楚，并核对它有没有独立契约。
- 抽取后应能集中验证复杂步骤，入口只验证自己的业务结果。若增加接口只是为了假设中的替换，或让测试更依赖内部调用方式，重新评估收益。
- 优惠规则、审批条件等业务逻辑仍用项目里的业务名称表达。提取后若调用方还要记住同样的细节，或看懂一次操作要打开更多文件，就没有解决原来的问题。

## 通用能力与依赖选型

查看项目是否在自行实现已有成熟方案的功能，例如字段校验、SQL 拼装与结果转换、缓存过期和淘汰等。比较现成方案能否少写、少测这些代码；一处复杂实现也值得看。类、SQL 或自写代码多只是线索，不能单独构成引入依赖的理由。

先比较语言或标准库能力、项目已有框架和依赖，再评估新增或替换库。说清哪些代码可以删、哪些业务判断还得自己写；简单本地逻辑和低优先级功能通常不值得承担迁移成本。

提出具体包的引入、替换或升级建议前，使用包管理器或 registry 元数据、官方文档和项目用法查验当前证据，不凭记忆断言维护状态或 API。按项目约束评估：

- 维护与社区是否足以支持项目风险，API 是否稳定且有文档，许可证是否适用。
- 能否减少项目代码或提高可靠性，迁移收益是否值得成本。
- 安全、体积、原生构建和运行环境是否适配；对不确定项说明证据缺口。
- 库的类型、参数和错误处理是否到处出现，集中到模块、adapter、hook 或组件后能否减少重复修改；仅转发调用的一层包装未必有用。

有多个适配的候选时，结合技术栈、行为契约、预期收益及接入和长期维护成本给出推荐顺序，说明主要取舍，供用户选型。无需为凑选项列出不适配的库；证据不足以排序时，指出还需核实的条件。

可选结论包括保留、引入、替换、隔离依赖、提取本地模块或暂不重构。当前方案够用、迁移主要制造改动，或关键约束尚不清楚时，可保留现状或暂缓建议。

## 判断边界

用同一个实际任务比较改前改后：入口少写哪些步骤，规则少改哪些位置，需要新增哪些接口、测试和迁移工作。局部函数或现有模块内的封装就可能够用；无需预先完成选型或全项目重构方案。

表面相似但独立变化的业务行为应分别保留。包的流行程度、较新版本或代码量减少，本身不足以构成问题。

## 判断示例

以下库名帮助说明候选方向，不是固定名单或引入建议。实际评估仍按项目语言、框架和上面的查证、排序要求进行。

### 三个同步任务都在自己翻页和重试

`sync_users`、`sync_orders`、`sync_refunds` 都写了同一家服务的“取一页、失败重试、更新游标、继续下一页”。改重试上限时要改三处。

判断：可评估提取共同的翻页请求函数，让三个任务各自处理拿到的数据。先确认它们的分页结束条件和重试规则相同；任务自己的失败预算可以继续分别设置。

### 只调用一次的上传函数也值得保留

业务入口只写 `upload(file)`，函数内部负责分片、断点续传和失败清理。整个项目只有这一个调用点。

判断：保留封装。内联后，业务入口就要重新处理这些步骤；调用次数少不是删除它的理由。

### 公式一样，业务规则未必相同

优惠券和会员折扣现在都算 `price * 0.9`，但产品计划下月只调整会员折扣。

判断：分别保留。合成一个“通用折扣函数”后再传入一组模式参数，反而容易让两套独立规则互相影响。

### 很多 class 都在手写相同的字段校验

项目里的请求 class 到处写着 `if age < 0`、邮箱检查和字符串转数字；增加字段时，构造函数与多处校验都要改。另一些 class 只有字段、构造函数和比较方法。

判断：前一类可比较 Python 的 Pydantic、TypeScript 的 Zod，或项目已有模型能力；后一类可先看 Python `dataclass`、Java `record` 等语言能力。类有独立业务行为时保留职责；迁移前核对自动转换、校验时机和报错格式会不会改变。

### 到处手写相似 SQL 和行数据转换

多个模块反复拼 `SELECT id, name FROM users WHERE id = ?`，再把查询结果逐字段装成对象；新增字段时要同步修改多处查询和转换。

判断：可比较现有查询工具，以及适配项目的 SQLAlchemy、Django ORM、Peewee 等候选，按收益和成本给出顺序。先核对事务和实际查询行为；几条清楚的 SQL 或专门优化的复杂查询，可以继续保留。

### 一个缓存文件也可能值得换成熟库

Java 项目用 `Map`、时间戳和清理线程实现过期、容量淘汰，还自己处理并发加载；这些逻辑只在一个文件中，却要维护很多边界测试。

判断：可比较 Caffeine 等适配语言的缓存库，看看能删掉多少过期、淘汰和并发控制代码。先核对失效及一致性要求；哪些数据允许缓存、何时主动刷新，仍由业务决定。

### 新框架更流行，但没有解决当前问题

现有库满足需求，也没有反复补丁或难以维护的代码，建议只写“换成更流行的框架”。

判断：不形成 finding。还缺少现有方案的具体不足、迁移收益和当前依赖证据。
