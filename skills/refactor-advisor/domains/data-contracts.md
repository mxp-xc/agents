# 数据与契约

顺着输入、API、业务模型和存储检查同一字段的含义是否一致：金额有没有弄错单位，未填写与主动清空能否区分，改一个字段时要同步修改哪些地方。

## 检查重点

- 沿数据写入、读取和输出核对单位、精度与舍入、时区、枚举值，以及缺失、`null`、空值和默认值的区别。同名或同类型的字段未必含义相同；一种数据在不同位置也可以使用不同格式。
- 阅读模型声明、接口约定、序列化与反序列化代码，核对转换有没有丢掉业务需要的信息。检查自动转类型、截断小数、未知枚举兜底或填默认值后，调用方还能否分清原来的输入。
- 查找多个入口各自维护的转换、校验或字段映射，列出规则变化时要一起改的位置；也检查是否两层都以为对方已经校验。分别判断格式是否合法、业务是否允许、能否写入存储，不能仅因都有校验就删掉其中一层。
- 选取当前需求、已有业务变体或近期字段变更，追踪哪些调用处、映射、读写代码和测试要一起修改。即使当前值一致，也检查同一规则是否需要手工更新多份；为不同接口适配格式则可能是必要工作。
- 结合实际读取路径检查已有数据能否被正确解释；只改类型声明或 schema，不能证明契约已经一致。

## 判断边界

内部模型、外部 DTO 和存储结构可以独立设计。先确认哪些含义必须一致，再判断各处为何使用不同格式、由谁校验、是否需要一起修改。输入格式校验与业务校验可能都需要保留；相同字段或校验表达式不能单独证明重复维护。

指出字段含义由哪份接口或业务规则定义，哪里负责转换和校验。用同一次字段变更比较改前、改后要修改和验证哪些位置；可以集中同一规则，保留各接口的格式转换，无需全项目统一 DTO、共用 schema 或引入通用 mapper、代码生成。验证约定的输入、输出和往返转换。

区分现在就会算错、丢值的问题，与下一次字段变化时容易漏改的问题。涉及数据调整时，核对旧数据能否读取、先部署哪一端及尚未确认的限制；是否需要兼容处理取决于真实调用方和部署方式，不默认添加兼容层或版本链。

安全审计不属于本领域的主要检查目标。

## 判断示例

- 支付页面和 CSV 导入都把元转成分，按业务要求应使用同一舍入规则，但一个四舍五入，另一个直接截断，同一笔金额因此不同。应报告金额转换不一致，并核对两个入口的边界值测试。
- API 和 CSV 导入各存了一份允许的订单状态，当前都正确；新增“已取消”时，要手动改两份列表、转换代码和测试。可评估集中同一状态规则，两种 DTO 仍保留各自格式校验；先确认两处确实允许同一组状态。
- `PATCH` 只修改姓名，没传 `remark`，旧备注却被清空，因为代码把“没传”和 `remark: null` 都转成了 `null`。若约定没传表示不改、传 `null` 才清空，应报告这次转换丢掉了区别，并验证部分更新行为。
- API 返回带时区的时间字符串，业务代码用时间对象，数据库存 UTC；转换后仍是同一时刻，跨时区测试也通过。三种格式可以保留，不必统一成一种类型。
- 公开商品 API 只允许可售状态，库存内部还要保存“盘点中”；转换代码明确拒绝把“盘点中”暴露给外部。应保留两套状态和相应校验，统一枚举可能误放开公开接口。
