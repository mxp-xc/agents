# 架构与可维护性

检查一项功能分散在哪些文件、业务规则由哪里维护，以及改一条规则要跟着改哪些地方。优先关注核心流程、状态变化、数据保存和外部调用，以及近期反复修改的代码。

## 检查重点

- 从用户操作或任务入口追到数据读写，检查一个模块是否同时处理无关事务、调用方是否直接修改另一层的内部字段。分析循环依赖时区分运行期、类型引用和延迟导入。
- 检查调用一个业务操作前，是否必须先改内部状态、按顺序调几个方法、准备特殊配置，再自行处理失败。结合现有调用点，评估能否由该操作内部完成这些步骤。
- 查找重复写在下单、退款、导出等入口的费率、状态判断和格式规则。核对它们是否确实遵循同一规则，或本来就应按租户、地区、版本分别变化。
- 选一次近期修改或明确的新需求，列出要一起改的接口、条件、字段映射和测试。比较调整后能少改哪些文件，也计入新接口、跨文件查找和迁移的成本。
- 优先考虑局部抽取、收窄接口或复用已有模块。设计模式应能解决具体的重复修改或调用顺序问题；为未来扩展增加结构时，要有现有变体、明确需求或计划支撑。

## 判断边界

先识别架构文档中的明确约束，在约束内评估方案；现状描述与设计理由用于理解取舍。流程集中写在一个函数或文件中，也可以在内部提取重复判断、减少参数或隐藏内部状态。

建议应说清调整哪几处，能少找哪些文件、少记哪些步骤或少改哪些地方。若换目录、增加一层后，调用方仍要记住同样的步骤，或拆分后反而要传递大量共享状态，继续寻找更小的调整；收益不足时保留现状。

## 文件与目录组织

对于已有多个协作文件或明确扩展计划的重要特性，评估是否应集中到独立目录或 package，内部按职责命名，子领域形成后再增加层级。关注同一特性以 `feature_*.py` 等名称平铺、与无关代码混杂，造成定位和修改困难的情况。

简单、独立的小功能可以保留单文件。也检查层级过深、透传入口和同一职责过度碎片化的问题；共享前缀或文件数量只能作为线索。

建议归组或拆分时，说明职责边界和收益，必要时给目标目录树。涉及搬迁时提示需核对的导入、动态入口、资源路径或测试归属，不要求在检查阶段制定完整迁移方案。

涉及代码搬迁时，同时核对相关文档的目录说明、模块入口和链接。

## 规模参考

对项目未规定的代码规模项，使用以下数值寻找值得深入阅读的位置：

| 对象 | 排查参考 |
| --- | --- |
| 文件 | 500 行供参考；超过 800 行分析，超过 1000 行重点分析 |
| 函数 | 超过 100 行分析，超过 200 行重点分析 |
| 嵌套 | 超过 3 层时检查各层是否必要 |

行数含 import、注释和声明，函数行数计入嵌套定义。结合业务逻辑、模型声明、测试或生成代码的性质评估，必要时区分主要篇幅。

超出数值只触发分析，不直接构成 finding。文件职责集中可以支持保留整体，也要检查局部规则是否重复、调用接口是否泄露细节。拆分后若仍需传递大量局部变量、整份对象或互调私有方法，应重新评估边界。

## 判断示例

### 调一次费率，要改三个文件

`checkout.py`、`refund.py` 和 `reconcile.py` 都写了 `fee = amount * 0.006`。现在结果正确，最近调整费率也没有漏改。

判断：仍可报告重复维护机会。若三处确实使用同一结算费率，可集中费率计算，各入口继续处理自己的流程；改完只需在一处改规则、验证边界。退款若有独立费率，就保留区别，不能凭公式相同合并。

### 协议规定的常量无需配置化

解析器写着 `HEADER_BYTES = 8`，协议规定帧头就是 8 字节。

判断：保留常量。没有其他协议版本或可变需求，仅因数字写在代码里就增加配置项，没有维护收益。

### 长文件可以只改重复的几行

订单流程按项目约定集中在一个文件，三个入口都检查 `state in {"PAID", "READY"}` 后才允许发货；新增可发货状态时要改三处。

判断：保留文件和流程，评估在文件内提取 `can_ship(state)`。先核对三处的发货条件确实相同；集中这项判断后即可停止，无需为它新建模块或分层。

### 同一特性的文件散落在上级目录

报告导出已有 CSV、PDF 两种格式，PDF 还包含独立的排版逻辑。修改导出功能时，经常要在混有其他特性的上级目录里找这几个文件：

```text
projects/
  report_export.py
  report_export_csv.py
  report_export_pdf.py
  report_export_pdf_layout.py
```

判断：可报告文件组织问题。核对导入关系后，可评估把这些文件归到一起，让维护者从导出目录找到入口和各格式的实现：

```text
projects/
  report_export/
    export.py
    csv.py
    pdf/
      render.py
      layout.py
```

实际布局沿用项目命名与 package 约定。若只是一份独立的小型导出脚本，保留单文件即可。

### 长文件有合理的保留依据

`protocol_v1_models.py` 超过 1000 行，大部分是同一协议的消息类型和字段声明。一次字段调整常要对照这些声明，没有混入业务流程。

判断：需要重点阅读，但不单凭行数要求拆分。若拆成多个文件只会增加来回查找，保留整体；仍要核对是否有与协议无关的逻辑混入。
