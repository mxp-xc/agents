# 状态与生命周期

检查谁能修改状态、修改何时生效，以及连接、文件和后台任务由谁创建、接手和清理。重点找出漏更新、漏清理，以及调用方必须自己记住的先后顺序。

## 检查重点

- 找出修改共享状态的入口，检查每个入口是否都维护了应当一起变化的数据。例如，修改商品数量后，总价是否也更新。区分必须同步的副本与有意保留的历史快照。
- 追踪连接、文件、订阅、定时器和后台任务：谁创建，谁只是借用，交给别人后谁负责结束。沿正常返回、提前返回、初始化失败、取消和关闭路径检查漏清理、重复关闭，以及任务继续访问已失效对象的情况。
- 检查事务、锁和临时状态是否覆盖完整操作。失败时应回滚的内容是否回滚，锁是否释放，结果是否在保存完成前就被发布，接手之后原调用方是否还在修改同一份数据。
- 检查每个调用方是否都得记住先初始化、再修改、再提交、最后清理。即使当前顺序都正确，也要看新增入口是否还得复制同一套步骤和失败处理，以及修改顺序时要同步改几处。
- 判断并发问题时，确认哪些状态共享、哪些读写可能交错，已有串行执行、版本校验或取消措施是否足够。仅有 `async`、回调或多个入口不能证明存在竞态；发出取消请求也不代表后台任务已经结束。

## 判断边界

只追踪目标中实际存在的状态和退出路径，无需为所有对象画完整状态图。增加状态机、类或锁，应能解决具体的修改权、先后顺序或清理问题。

先确认框架、连接池或任务管理器已经负责什么。如果它覆盖了正常、异常和取消时的清理，使用方可以不再重复关闭资源。已有保障能排除相应泄漏风险，但不能自动排除多个入口分别维护提交、通知等共同步骤的成本。请求结束后仍会运行的任务，要单独确认谁持有它、何时停止它。

建议说清楚哪些步骤可以交给同一处负责、调用方少记住什么、哪些退出路径不必重复验证。不同操作若有不同的提交或清理条件，可以各自管理；局部封装足够时，做到这里即可，无需统一事务框架或全局状态机。

## 判断示例

- 购物车增删商品时会更新总价，修改数量时却只改明细，结算继续读取旧总价。这是漏更新问题，可以评估统一修改入口或在读取时计算总价；仍需保留原有折扣、舍入和结算快照规则。
- 用户从账号 A 切换到 B，程序取消了 A 的请求，但请求捕获取消后仍把 A 的结果写到当前页面；写入前也不检查账号或请求版本。这条路径会覆盖 B 的页面，值得报告；只调用 `cancel()` 还不足以排除问题。
- CSV 和 JSON 导入都分别写了一套“建临时文件、写完后原子发布、失败或取消时删除临时文件”。当前没有错误，但修改发布条件时必须改两套。可以评估集中发布和清理步骤，让各格式只维护自己的写入逻辑。
- 框架的事务作用域已经保证正常时提交、异常或取消时回滚，并把连接归还连接池；业务函数也没有把连接带出作用域。可以保持现状，不因业务函数没写 `close()` 报告泄漏，额外关闭反而可能打断后续操作。
