# 代码简化

检查能否在保持行为不变的前提下，减少分支、重复保存的数据和无用跳转，让代码更容易读懂和修改。

## 检查重点

- 查找深层嵌套、复杂条件和嵌套三元表达式，判断提前返回、局部命名函数或关键中间变量是否能理清逻辑。
- 检查复杂回调链是否适合用 `async` / `await` 表达，保留原有异常处理和执行时序。
- 追踪一个值从哪里来、在哪里修改、被谁读取。查找只写不读的字段、能直接算出却反复更新的状态，以及没有用途的中间转换；即使当前结果正确，也要检查新增分支时是否容易漏改某次赋值。
- 查找晦涩命名、冗长表达式和表达同一规则的局部重复代码。使用有业务含义的名称；拆开长链或使用解构，以更容易理解为准。
- 检查不可达代码、无用导入、废弃分支、注释掉的实现和遗留调试输出。区分调试输出与有用途的业务日志。
- 顺着一次读取或写入检查 helper：每层是在校验、转换或处理复杂规则，还是只把相同参数交给下一层？指出哪些跳转可以省去，以及省去后调用处会不会变得更复杂。

## 判断边界

认定代码无用前，结合使用方式核对调用方、对外导出、动态注册、配置引用及加载副作用等间接用途。搜索不到直接调用，只能作为排查线索。

说明简化前后为何得到相同结果，按改动核对返回值、异常、表达式求值与副作用顺序、异步时序、资源释放和对外契约；还不能确认的差异要写清楚。

以可读性和维护收益判断，保留项目风格。行数减少、调用次数少或个人语法偏好本身不足以构成问题；有调试价值的中间变量、隐藏复杂度或提供有效测试边界的抽象仍有价值。

说明改后少更新了哪些字段、少走了哪些分支或 helper。简化建议以让目标代码容易读懂为限；把几行压成难读的表达式，或让每个调用处重新处理同一套规则，都可能得不偿失。

删除或简化入口、分支与配置时，核对相关文档和示例是否仍适用。

## 判断示例

- 读取客户姓名要经过三个私有 helper，每个都原样转发参数，最后只返回 `customer.name`。可以评估去掉中间转发；先确认它们没有导出、动态引用或独立用途。
- 每次增删 `items` 都要手动更新 `isEmpty`，现在测试全绿。若读取方只关心当前数组是否为空，可直接检查 `items.length === 0`，省去同步赋值；外部可写、历史快照或变更通知另有约定时先核对这些用途。
- `send_report` 没有直接调用点，但配置写着 `handler: send_report`，程序启动时会按名称注册。它仍在使用，不能凭搜索不到调用就删除。
- `await saveOrder()` 后才执行 `await sendReceipt()`；改成 `Promise.all` 可能在订单保存完成前发出收据。代码虽然更短，也不能作为保持行为不变的简化。
