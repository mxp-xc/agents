# 性能与数据访问

结合实际数据量、调用频率和已有测量，检查哪些计算、查询或数据保留可以减少。代码能证明每增加一条数据就多一次查询，也足以作为排查成本增长的线索。

## 检查重点

- 沿一次请求或任务统计数据访问次数，查找重复 IO、N+1、循环中反复扫描和重复计算。核对 ORM 的延迟加载、预加载和请求内复用，确认是否真的访问了外部服务；也检查多次读取是否为了取得最新数据或保证一致性。
- 检查查了多少数据、用了哪些字段、分页和批次是否有上限。关注只需计数却加载所有记录、先全量读入再分批写出，以及循环结束前一直保留中间结果的情况。
- 检查同时发出多少请求、还有多少任务排队，这些数量是否直接跟输入条数一起增长，会不会超过连接池或下游限流。串行 `await` 可能是为了顺序、事务或限流，应先查清再建议并发。
- 检查同步 IO 和重计算在哪里执行：阻塞请求线程或事件循环，与启动时读少量配置的影响不同。使用已有 trace、profile、查询计划、监控或基准结果核对耗时，并记录对应的数据量和运行条件。
- 比较批量处理或缓存能减少哪些实际工作。批次要考虑查询参数、响应大小和事务范围；缓存要核对哪些结果能复用、键如何区分、容量和失效方式、允许使用多旧的数据，以及不同租户能否隔离。

## 判断边界

把输入条数与新增工作联系起来。每条记录多一次查询、一次性发出无上限的请求，或把不断增长的数据一直留在内存里，都可以报告成本增长风险，无需先跑 benchmark。这还不能证明当前已经很慢、必然耗尽资源，或改完能快多少；需要测量才能判断的部分要明确指出。

有循环、`await`、全量读取或没有缓存，本身不构成问题。数据量小且有稳定上限、测量满足要求，或优化收益抵不过新增复杂度时，可以保持现状。

先去掉不用的数据、重复查询和重复计算，再比较批处理、并发、缓存或算法调整。说明能少做什么，以及新增缓存状态或并发控制要维护什么。调整建议以减少目标路径的重复工作，或让资源用量具有满足要求的明确边界为限。调整仍需保留结果顺序、缺失项、部分失败、事务一致性、下游限流和取消行为；若方案必须改变这些约定，直接说明。

使用已有测量或提出验证方案，在相同数据量下比较查询次数、峰值内存或耗时，同时检查业务结果是否保持一致。

## 判断示例

- 假设列表显示 100 笔订单，先查一次订单，再为每笔订单单独查客户；代码和 ORM 配置确认每次都会访问数据库。这次请求会查 101 次，值得评估按客户 ID 批量查询。没有测量时不能声称会快多少；改后仍需保持订单顺序和客户缺失时的处理方式。
- 导出先把全部历史记录读进数组，再每 500 条写一次文件。历史记录持续增加，数组却到导出结束才释放。分批写出没有减少读取侧的常驻内存，可以评估分页或流式读取；还不能据此宣称已经发生内存不足，分批读取也要核对排序和导出期间的数据一致性。
- 一个任务最多处理 8 项，下游要求前一项完成才能提交下一项；已有同规模测量满足时限，各项结果也不复用。可以保留循环里的 `await`，不必为了并发或缓存增加额外控制。
