# 文档与知识维护

检查当前文档能否让人找到入口、按步骤操作，并读懂项目约定。关注多处重复更新、内容过时、话说不清和目录难找。检查范围按入口约定确定。

## 检查重点

- 对照代码、配置、命令注册和适用契约，核对文档里的命令、参数、路径和前置条件。先分清它描述的是当前行为、已批准计划还是历史决策；不一致可能是文档旧了、代码写偏了，也可能适用于不同版本。
- 找出哪些环境变量、操作步骤或规则在多份文档里完整写了一遍。即使现在都正确，也查看改一次要更新几处；比较保留一份正文、其他位置放摘要和链接是否更省事、更好读。
- 跟着“首次启动”“部署一次”“定位一个故障”等具体任务，检查标题、目录和链接：能否找到正确入口，是否来回打开无关页面，链接和锚点是否有效。按主题和读者需要评估归组、合并或局部拆分，沿用项目现有文档体系。
- 查找空泛承诺、重复解释和无用铺垫，评估把“进行处理”等含糊动作写具体。给出改写建议时保留术语、适用范围、前提、例外和完成条件，让读者知道何时读、做什么、做到哪一步算完成。

## 判断边界

合并应减少反复更新同一内容的工作，也要计入阅读跳转和搬迁成本。给不同读者的必要摘要、独立版本的说明、产品契约、审计记录及仍有解释价值的 ADR 可以保留；不以字数或文件数量判断冗余，不把所有内容集中到一份长文。

建议搬迁、合并或删除时，查哪些页面链接到它，以及相对路径、锚点和文档构建入口是否会失效。自动生成的文档应修改模板或数据源，不直接改生成结果；能从配置查到的细节，仍可能需要使用入口和必要解释。

核实命令时优先读取注册入口、配置和现有验证结果，不为核对文档去执行写入、部署或清理操作。证据不足时列出差异和待确认事项，不能为了与代码对齐而改掉有效约束。

本领域负责文档内容及导航；代码职责、目录布局和实现精简只沿相关线索核对，不扩展为完整代码审查。

## 判断示例

### 改一个启动参数，要更新三篇文档

以下三处都完整写着同一组环境变量和启动步骤，当前内容一致；上次改参数时也正确更新了三份：

```text
README.md
docs/deploy.md
docs/operations.md
```

判断：可报告重复维护机会。可让部署指南保留完整步骤，README 和运维手册保留用途、必要差异及链接。若读者因此要反复跳转才能完成任务，则保留所需的短摘要。

### 文档与代码不一致，先确定该改谁

API 文档写着“提交超时后，先用请求 ID 查询结果”；代码却在超时后直接再次提交，且没有证据表明该契约已经调整。

判断：报告这处差异，核对设计和调用方后再确定改哪边。直接把文档改成“超时后重试”，可能会掩盖重复提交的实现问题。

### 同一句命令，可以服务不同读者

快速开始用 `app start` 帮新人首次运行；故障手册也写了这条命令，但要求先备份、检查端口。`docs/archive/v1-deploy.md` 明确记录旧版部署方式，当前入口没有误链到它。

判断：保留两处有用途的短命令和各自前提，归档默认不查不清理。若 v1、v2 仍各有受支持用户，操作说明也可按版本分别保留，不能混成一套步骤。

### 简短改写要保留操作条件

原文：

> 为确保系统稳定可靠地运行，在本地环境首次启动且尚未创建配置文件时，您需要先完成配置文件的初始化操作。

可改为：

> 本地首次启动且配置文件不存在时，先初始化配置文件。

判断：删掉空泛承诺和绕口表达，保留“本地”“首次启动”“配置不存在”三个前提。若文中已有清楚的命令入口，链接到它即可，无需再复制一套步骤。
