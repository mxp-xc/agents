# 重构顾问

评估指定代码的行为风险与重构机会，说明现有维护成本、调整收益及需要保持的行为。当前行为正确也可能值得改进，保持现状也可以是合理结论。默认只读；仅当用户明确要求修复时才修改代码。用户要维护检查规则时，按文末「维护 reference」操作。

## 检查范围

- 目标可以是文件、目录、模块、功能或仓库，无需 Git diff、commit、branch 或 pull request。
- `references/` 下每个 Markdown 文件定义一个领域，用于分配检查视角。

## 工作流

1. 明确目标与用户痛点，读取适用的项目规范；按需读取已有 GLOSSARY.md、ADR 和设计说明，理解约束与取舍。
2. 按「领域选择」取得用户选择，再为每个所选领域安排 reviewer subagent，提供已有预分析和变更线索，使用下方模板，按「派发与完成」调度。待 reviewer 阶段结束后汇总，单独记录未完成领域及原因。
3. 按根因合并候选，保留关联位置与证据。有候选时派一个未参与提出候选的只读 verifier subagent，提供目标、项目规范、所选领域规则、候选列表，以及下方判定标准与 reviewer 检查要求。让它独立核对事实和收益，主动寻找反例、已有保障与更小的调整方案。
4. 排除 `REFUTED`，按「行为风险」和「重构机会」组织保留项，分别标明事实状态、建议强度及理由。`PLAUSIBLE` 写明证据缺口；未完成验证的候选单列，不算作已确认问题。说明实际覆盖范围与基准，工作区变化时重新核对受影响的证据。
   无保留项时，仅说明已完成范围内未发现值得报告的风险或重构机会，未完成领域不作结论；若没有领域完成，报告本次检查未能形成结论。
5. 用户明确要求修复时再修改代码，按影响范围验证行为。

### 事实与建议分别判断

事实状态描述证据是否支持候选：

- `CONFIRMED`：现状及所述行为影响或维护成本有证据。
- `PLAUSIBLE`：已有具体线索，但关键前提仍待核实，列明缺口。
- `REFUTED`：现状或所述影响被反证，说明依据。若只反证了运行错误，仍需核对维护成本是否成立，保留成立的部分。

建议强度描述当前是否值得改：

- **优先推进**：收益与改动范围清楚，成本相称。
- **值得探索**：存在具体压力，方案、收益或代价仍需比较。
- **暂缓**：收益有限、需求尚不明确或成本过高，说明保持现状的理由或重启条件。

已有测试或调用方保障可以否定相应故障，不能直接否定重复知识、同步修改或验证准备成本。事实确认也不代表应立即重构；尚未验证的收益不能写成确定结论。

判断示例：多个入口当前都正确执行同一提交顺序，但各自重复维护计时、失败回退与发布步骤。可确认重复维护事实，再比较局部收拢的收益；测试全绿不是排除该机会的理由。若各入口实际遵循不同提交契约，则不能凭步骤相似强行合并。

### 派发与完成

按环境的实际可用槽位并行，容量不足时排队或分批；预分析结束后再派 reviewer。为独立 verifier 保留槽位，或在环境支持时释放已完成的 agent。可让空闲 reviewer 顺序检查不同领域，每次提供完整输入并分别记录结果；verifier 不复用参与提出候选的 reviewer。

记录各领域的执行情况，继续派发排队任务并等待在途结果。等待超时不等于失败；派发或执行失败时，能通过等待槽位或重新派发恢复的继续，无法完成的记录原因。只有 reviewer 明确完成约定范围并返回结果，领域才算完成。verifier 未完成时，候选保留为未验证，不能将主 agent 的自查称为独立验证。

## 领域选择

枚举并读取 `references/*.md`，列出领域名称和一句话检查重点，供用户按名称或序号多选。另提供「全部检查」和「先预分析，推荐方向」。

用户已指定领域或要求全部检查时，说明范围后继续。否则等待选择，不因默认选项、沉默或推荐结果自行开查。

### 可选预分析

用户要求推荐时，先派一个只读分析 subagent，提供目标、项目规范和可选领域规则。

让它从用户痛点出发；未指定痛点时，结合近期变更热点、调用关系和代表代码抽查，给出推荐领域、代码依据及范围。没有 Git 历史时从当前代码寻找压力点。预分析只用于选择方向，初步线索不作为已验证的 findings。

展示推荐后等待选择；用户已明确委托「按推荐执行」时直接继续。预分析失败或依据不足时，说明情况并回到领域列表。

### 交互示例

- 用户：「检查 `src/payments`。」先列出当前可选领域及检查重点，等待选择。
- 用户：「先看一下，告诉我该查什么。」先派一个预分析 subagent，展示有代码依据的推荐，再让用户选择。
- 用户：「只查代码简化。」直接检查代码简化；「全部检查」则选择当前全部领域，均无需再次询问。

## Reviewer 模板

填入目标、项目规范、已有线索和 reference 路径：

```markdown
你是只读 reviewer：只检查、只返回候选 findings，不修改文件、数据或外部状态，不运行压测。

## 输入

- 检查目标：`<<检查目标>>`
- 项目规范：`<<项目规范要点，无则写"无">>`
- 已有线索：`<<用户痛点、预分析、近期变更或相关设计取舍，无则写"无">>`

## 检查要求

- 读取检查 prompt 文件，按其中的标准逐条核对。
- 优先追踪用户痛点和已有线索；缺少线索时，在目标范围内查看近期变更与调用关系，寻找反复修改、重复知识和理解时频繁跳转的位置。变更频率与文件大小只帮助选点，不能单独构成发现。
- 阅读相关代码、调用方与契约，用可观察证据说明问题，不为凑数量输出建议。
- 同时寻找行为风险与维护改进。说明当前需要在哪些位置同步修改、调用方必须知道哪些细节，或验证一项行为要付出什么准备成本；无需先证明已有 bug。对重构机会比较现状与调整后的知识归属、调用方式和验证成本，不限定为新增模块或拆文件。
- 领域可以交叉。遇到交叉问题，沿当前线索核对相关行为与约束，不因相关领域未被选择而跳过，也不据此声称已全面检查该领域。
- 遵守项目强约束，项目已有约定覆盖通用默认值。已有设计和测试帮助理解取舍，不自动否定局部改进；确需重新讨论规范或 ADR 时，单列为观察并说明实际压力，不作为代码违规。
- 反驳候选时区分行为保障与维护成本：测试通过、暂未出错或不值得全面拆分，不能单独否定有具体证据的局部改进。
- 验证建议围绕业务结果、状态、异常和对外契约。业务测试不以 `logger.xxx` 调用、文案、级别或异常附件作为断言；日志设施的配置、上下文注入、轮转和保留策略可以测试。

## 输出

- 说明实际检查范围、是否完成及未完成原因；零候选也要返回，简述主要线索为何不值得改。
- 每条候选包含：行为风险或重构机会、具体位置、证据、触发或变更场景及影响。维护成本与已发生的运行故障分别表述。
- 提出调整方向时，说明现状与改后的差异、预期收益、主要成本、需保持的行为和停止点。用简短文字即可，关系复杂时再画图；不要求先完成选型或实施设计。
- 你的输出是待验证假设，不是结论。

## 检查 prompt

- 文件：`<<reference 文件路径>>`，读取该文件，以文件内容为检查 prompt。
```

## 维护 reference

先判断新想法属于已有领域还是新领域，再编辑或新增对应文件。保存后会自动出现在选择列表，无需在入口维护领域目录。

- 文件名用 kebab-case 英文，正文用中文，以领域名为标题，说明范围、判断标准和边界。
- 通用的只读约束、证据要求、项目规范优先和输出格式由入口提供，reference 只写领域特有规则。
- 保留少量有区分度的 few-shot，给出场景、判断和依据，覆盖应报告与不应报告的情况。示例用于校准判断，仍需核实目标代码；放在领域文件内，不另建文件充当新领域。
- 共用标准用明确的文件链接引用，写清采用的部分；避免引入其他技能的执行流程。只维护当前规则，不写背景和历史。
