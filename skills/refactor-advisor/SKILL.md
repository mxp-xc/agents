# 重构顾问

评估指定代码与当前项目文档的风险和重构机会，说明现有维护成本、调整收益及需要保持的行为或含义。当前内容正确也可能值得改进，保持现状也可以是合理结论。默认只读；仅当用户明确要求修复时才修改文件。

## 检查范围

- 目标可以是文件、目录、模块、功能或仓库，无需 Git diff、commit、branch 或 pull request。
- `domains/` 下每个 Markdown 文件定义一个领域，用于分配检查视角。

## 共用规则

项目的明确要求优先于本 skill 的通用默认值，未规定的部分才采用默认规则。这一优先级适用于所有领域，包括代码组织、规模、命名、测试及文档约定。区分强制要求与现状描述；确需重新讨论规范或 ADR 时，单列为观察并说明实际压力，不作为代码违规。

### 相关项目文档

各领域都按目标核对相关的 README、`docs/`、使用与运维说明等，不限文件后缀。结合项目导航、配置引用和近期变更定位当前使用的内容；更新时间久、没有直接引用，都不能单独证明文档过时或无用。

明确归档的文档默认排除。若当前入口仍指向归档内容，只沿线索核对该引用是否误导，不展开归档清理。文档是约束与证据，也可能是改进对象；完整的合并、措辞和导航检查由所选的[文档与知识维护](domains/documentation-maintainability.md)领域负责，其他领域只追踪相关线索。

## 工作流

1. 明确目标与用户痛点，读取适用的项目规范和相关当前文档；按需读取已有 GLOSSARY.md、ADR 和设计说明，区分约束、现状描述与计划。代码和文档不一致时，依据契约、配置、测试及决策记录判断哪一方需要调整，不能默认文档过时。
2. 按「领域选择」取得用户选择，再为每个所选领域安排只读 reviewer subagent，按「派发与完成」提供文件引用与任务上下文。待 reviewer 阶段结束后汇总，单独记录未完成领域及原因。
3. 按根因合并候选，保留关联位置与证据。有候选时派一个未参与提出候选的只读 verifier subagent，提供候选及相关证据入口，让它按本文件的判定标准与检查要求独立核对事实和收益，主动寻找反例、已有保障与更小的调整方案。
4. 排除 `REFUTED`，按「行为风险」和「重构机会」组织保留项，分别标明事实状态、建议强度及理由。`PLAUSIBLE` 写明证据缺口；未完成验证的候选单列，不算作已确认问题。说明实际覆盖范围与基准，工作区变化时重新核对受影响的证据。
   无保留项时，仅说明已完成范围内未发现值得报告的风险或重构机会，未完成领域不作结论；若没有领域完成，报告本次检查未能形成结论。
5. 用户明确要求修复时再修改文件，按影响范围验证行为、文档含义及引用。

### 事实与建议分别判断

事实状态描述证据是否支持候选：

- `CONFIRMED`：现状及所述行为影响或维护成本有证据。
- `PLAUSIBLE`：已有具体线索，但关键前提仍待核实，列明缺口。
- `REFUTED`：现状或所述影响被反证，说明依据。若只反证了运行错误，仍需核对维护成本是否成立，保留成立的部分。

建议强度描述当前是否值得改：

- **优先推进**：收益与改动范围清楚，成本相称。
- **值得探索**：存在具体压力，方案、收益或代价仍需比较。
- **暂缓**：收益有限、需求尚不明确或成本过高，说明保持现状的理由或重启条件。

已有测试或调用方保障可以否定相应故障，不能直接否定重复知识、同步修改或验证准备成本。事实确认也不代表应立即重构；尚未验证的收益不能写成确定结论。

判断示例：多个入口当前都正确执行同一提交顺序，但各自重复维护计时、失败回退与发布步骤。可确认重复维护事实，再比较局部收拢的收益；测试全绿不是排除该机会的理由。若各入口实际遵循不同提交契约，则不能凭步骤相似强行合并。

### 派发与完成

派发预分析、reviewer 或 verifier 时，优先引用本 `SKILL.md`、适用的领域文件、公共资源和项目规范，给出可访问的文件路径与需读取的部分，让 subagent 自行读取。派发 agent 自行组织 prompt，并按任务决定是否补充背景、线索、摘录或其他说明，无需先读取规则全文再复制到 prompt。

交代任务角色、检查目标与范围，让 subagent 能定位适用规则；文档排除项或候选等任务上下文按需提供。上述三个角色均只读，不修改文件、数据或外部状态，不运行压测。

按环境的实际可用槽位并行，容量不足时排队或分批；预分析结束后再派 reviewer。为独立 verifier 保留槽位，或在环境支持时释放已完成的 agent。可让空闲 reviewer 顺序检查不同领域，分别说明本次任务与适用文件并记录结果；verifier 不复用参与提出候选的 reviewer。

记录各领域的执行情况，继续派发排队任务并等待在途结果。等待超时不等于失败；派发或执行失败时，能通过等待槽位或重新派发恢复的继续，无法完成的记录原因。只有 reviewer 明确完成约定范围并返回结果，领域才算完成。verifier 未完成时，候选保留为未验证，不能将主 agent 的自查称为独立验证。

## 领域选择

枚举并读取 `domains/*.md`，列出领域名称和一句话检查重点，供用户按名称或序号多选。另提供「全部检查」和「先预分析，推荐方向」。

用户已指定领域或要求全部检查时，说明范围后继续。否则等待选择，不因默认选项、沉默或推荐结果自行开查。

### 可选预分析

用户要求推荐时，先按「派发与完成」派一个只读分析 subagent，引用可选领域文件。

让它从用户痛点出发；未指定痛点时，结合近期变更热点、调用与文档引用关系和代表内容抽查，给出推荐领域、依据及范围。没有 Git 历史时从当前代码与文档寻找压力点。预分析只用于选择方向，初步线索不作为已验证的 findings。

展示推荐后等待选择；用户已明确委托「按推荐执行」时直接继续。预分析失败或依据不足时，说明情况并回到领域列表。

### 交互示例

- 用户：「检查 `src/payments`。」先列出当前可选领域及检查重点，等待选择。
- 用户：「先看一下，告诉我该查什么。」先派一个预分析 subagent，展示有依据的推荐，再让用户选择。
- 用户：「只查代码简化。」直接检查代码简化；「全部检查」则选择当前全部领域，均无需再次询问。
- 用户：「检查 `docs/` 是否重复、过时，顺一下结构和措辞。」直接选择文档与知识维护，按需核对代码和配置，不扩展为完整代码审查。

## 检查要求

- 读取所引用的规则文件，结合项目要求核对当前目标。
- 优先追踪用户痛点和已有线索；缺少线索时，在目标范围内查看近期变更与调用关系，寻找反复修改、重复知识和理解时频繁跳转的位置。变更频率与文件大小只帮助选点，不能单独构成发现。
- 阅读相关代码、调用方、契约及当前文档，按给定文档范围核对命令、路径、规则和示例是否与当前入口对应；用可观察证据说明问题，不为凑数量输出建议。
- 既检查会不会出错，也检查是否难读、难改或难验证。沿一个具体需求，列出要同时修改的地方、每个调用方得记住的步骤，或测试前要准备的环境。即使当前结果正确，也能报告有证据的维护成本；说明调整后能减少哪些修改、步骤和测试准备，不必新增模块或拆文件。
- 领域可以交叉。遇到交叉问题，沿当前线索核对相关行为与约束，不因相关领域未被选择而跳过，也不据此声称已全面检查该领域。
- 已有设计和测试帮助理解取舍，不自动否定局部改进。
- 反驳候选时区分行为保障与维护成本：测试通过、暂未出错或不值得全面拆分，不能单独否定有具体证据的局部改进。
- 验证建议围绕业务结果、状态、异常和对外契约。业务测试不以 `logger.xxx` 调用、文案、级别或异常附件作为断言；日志设施的配置、上下文注入、轮转和保留策略可以测试。

### 返回结果

- 说明实际检查范围、是否完成及未完成原因；零候选也要返回，简述主要线索为何不值得改。
- 每条候选说明是行为风险还是重构机会，给出具体位置和证据，写清什么情况下有风险，或查找、读懂、修改、验证代码或文档时多做了哪些工作。维护成本与已发生的故障分开写。
- 提出调整方向时，说清当前怎么做、准备怎么改、能省哪些工作、要付出哪些代价，以及哪些行为或文档含义要保持、改到什么程度即可。关系复杂时再画图，无需先做完整选型或实施设计。
- reviewer 返回的候选是待验证假设，由 verifier 独立核对后再形成结论。
