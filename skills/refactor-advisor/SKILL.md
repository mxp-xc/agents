# 重构顾问

评估指定代码的重构机会，验证疑似问题，说明调整收益、成本及需要保持的行为。保持现状也可以是合理结论。默认只读；仅当用户明确要求修复时才修改代码。用户要维护检查规则时，按文末「维护 reference」操作。

## 检查范围

- 目标可以是文件、目录、模块、功能或仓库，无需 Git diff、commit、branch 或 pull request。
- `references/` 下每个 Markdown 文件定义一个领域。领域用于分配检查视角，可以交叉；汇总时按根因去重，不因分类忽略问题。

## 工作流

1. 明确目标，读取适用的项目规范（AGENTS.md、CLAUDE.md、lint 配置等），提炼要点。
2. 按「领域选择」取得用户选择，再为每个所选领域派一个 reviewer subagent，使用下方模板并行检查。收齐返回后汇总；未完成的领域单独说明。
3. 按根因合并候选，保留关联位置与证据。有候选时派一个只读 verifier subagent，提供目标、项目规范、所选领域规则和候选列表，让它读代码并主动尝试反驳每条候选，分类为 `CONFIRMED`、`PLAUSIBLE` 或 `REFUTED`，说明依据和证据缺口。
4. 排除 `REFUTED`，报告其余候选及本次检查范围。`PLAUSIBLE` 必须写明不确定性；未完成验证的候选单独列明，不能算作已确认问题。
   无候选时，仅说明已完成检查的范围内未发现问题，未完成领域不作结论；若没有领域完成，报告本次检查未能形成结论。
5. 用户明确要求修复时再修改代码，按影响范围验证行为。

## 领域选择

枚举并读取 `references/*.md`，列出领域名称和一句话检查重点，供用户按名称或序号多选。另提供「全部检查」和「先预分析，推荐方向」。

用户已指定领域或要求全部检查时，说明范围后继续。否则等待选择，不因默认选项、沉默或推荐结果自行开查。

### 可选预分析

用户要求推荐时，先派一个只读分析 subagent，提供目标、项目规范和可选领域规则。

让它按目标抽查目录、入口、依赖声明和代表代码，给出推荐领域、代码依据及抽查范围。预分析只用于选择方向，初步线索不作为已验证的 findings。

展示推荐后等待选择；用户已明确委托「按推荐执行」时直接继续。预分析失败或依据不足时，说明情况并回到领域列表。

### 交互示例

- 用户：「检查 `src/payments`。」先列出当前可选领域及检查重点，等待选择。
- 用户：「先看一下，告诉我该查什么。」先派一个预分析 subagent，展示有代码依据的推荐，再让用户选择。
- 用户：「只查代码简化。」直接检查代码简化；「全部检查」则选择当前全部领域，均无需再次询问。

## Reviewer 模板

填入目标、项目规范和 reference 路径：

```markdown
你是只读 reviewer：只检查、只返回候选 findings，不修改任何文件。

## 输入

- 检查目标：`<<检查目标>>`
- 项目规范：`<<项目规范要点，无则写"无">>`

## 检查要求

- 读取检查 prompt 文件，按其中的标准逐条核对。
- 阅读相关代码、调用方与契约，用可观察证据说明问题。领域可以交叉，围绕根因判断，不为凑数量输出建议。
- 以项目规范为准，项目已有约定覆盖通用默认值。确有必要讨论规范本身时，单列为观察，不作为代码违规。

## 输出

- 每条候选 finding 包含：具体位置、可观察证据、触发或变更场景、实际影响。区分维护风险与运行故障，建议的详细程度以解释问题所需为准。
- 你的输出是待验证假设，不是结论。

## 检查 prompt

- 文件：`<<reference 文件路径>>`，读取该文件，以文件内容为检查 prompt。
```

## 维护 reference

先判断新想法属于已有领域还是新领域，再编辑或新增对应文件。保存后会自动出现在选择列表，无需在入口维护领域目录。

- 文件名用 kebab-case 英文，正文用中文，以领域名为标题，说明范围、判断标准和边界。
- 通用的只读约束、证据要求、项目规范优先和输出格式由入口提供，reference 只写领域特有规则。
- 保留少量有区分度的 few-shot，给出场景、判断和依据，覆盖应报告与不应报告的情况。示例用于校准判断，仍需核实目标代码；放在领域文件内，不另建文件充当新领域。
- 共用标准用明确的文件链接引用，写清采用的部分；避免引入其他技能的执行流程。只维护当前规则，不写背景和历史。
