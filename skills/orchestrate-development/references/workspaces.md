# 工作区补充约定

采用共享工作区或独立 worktree 时，按需读取对应部分，处理已有改动、整合并发和资源清理。

## 共享工作区

- 派工前检查现有改动，记录哪些属于用户或其他任务。对并行写入指定文件或模块归属；公共接口、锁文件、全局配置和生成产物由明确的一位负责人修改。
- 每个负责人及其下级使用派工指定的工作目录，只修改自己的范围。读到其他任务尚在变化的代码时，不能把它当作已经验收的依赖产物。
- 测试会读取整个当前目录的代码。必要时协调相关写入停止后再运行集成检查；局部失败先确认使用的代码状态，避免因其他任务的中间状态修改无关代码。
- 由指定整合者统一执行需要的暂存和提交，检查提交是否混入其他人的改动；共享目录中并行执行 Git 写操作会互相影响。

## 创建、接管或嵌套使用 worktree

确认用户已授权本次所需的分支、worktree、提交和整合操作，记录授权边界。检查原工作区的未提交改动；从某个提交创建的 worktree 不会自动带入这些改动。任务若依赖它们，先明确获准的转移或形成基线方式，不能遗漏或覆盖。

基线不匹配时协调修正，保留已有成果，不使用破坏性重置自动纠正。

工作包必须写明 worktree 路径；负责人在执行命令、改文件和向下委派前都核对实际工作目录与工作包一致。下级在同一 worktree 中仍按共享工作区规则划分写入范围；另开 worktree 时要重新明确基线及向哪个目标交付。

## 整合补充

同一整合目标同一时间只交给一位整合者操作。协调者确定依赖顺序和整合范围；整合者可以是专门派遣的 agent，具体人数按工作量安排。

采用独立 worktree 并行时，派工前明确各工作区的基线、交付方式和整合者需要保留的行为及测试。整合者核对已验证的交付，按依赖顺序逐项整合；可独立交付的结果及时进入目标，不必等待其他任务全部结束。

不同工作区出现相近的公共实现时，整合者在已确认的合同和验收要求内，结合调用方和测试选定最终接口，合并所需行为并删除重复实现；需要较大修复时回交相应负责人。保留各任务的业务验收覆盖，不把重复实现简单并排留下。将整合中发现的共享能力和依赖更新到项目已有记录，供后续拆分复用。

发生冲突时，区分文本冲突和接口、行为上的冲突。整合者协调相关负责人解决冲突并确定修复归属；若需要在互斥合同之间取舍，或改变公共接口约定、任务范围或验收条件，先向派遣者说明事实、影响和待决定的问题，取得处理意见后再推进受影响部分。解决冲突后运行受影响的测试；即使 Git 未报告冲突，也要验证合在一起的行为。整合未完成前，不开始对同一目标的下一次整合，也不让下游使用中间状态。

## 清理条件

清理前确认结果已按实际采用的方式进入指定目标；非 merge 整合时，不能只靠分支合并状态判断。负责人和各级下级已停止相关写入，开发服务与测试进程已结束。

检查未提交改动、未跟踪文件和独有报告等材料，先保存需保留的内容。只移除已获授权且属于本次任务的 worktree、分支和运行资源；归属不明或仍在使用的资源保留并报告，不强制删除，不清理用户原有工作区或分支。

## 共享环境

首次使用或更换工作区时，确认解释器、依赖和工具配置是否可用，按依赖兼容性与隔离需要选择复用或独立准备。将选定的入口和必要参数随工作包向下传递；只读脚本也核对自动安装、写缓存或创建环境等副作用，按实际写入安排资源。

并行测试或服务分别分配端口、数据库/schema、测试账号、数据目录和其他会发生写入的资源。无法分配独立资源时，将其使用列为任务依赖并串行安排。worktree 的目录不同不代表这些资源已经隔离。

独立 worktree 仍属于同一 Git 仓库，不把它当作独立 clone；分支删除、仓库级配置等操作交由明确的负责人协调。
