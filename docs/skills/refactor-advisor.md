# refactor-advisor 维护说明

修改领域划分、共用规则、派发方式或展示文案前，先读本文，再定位对应文件。运行时规则以 [SKILL.md](../../skills/refactor-advisor/SKILL.md) 为准；本文说明维护边界，不参与领域发现。

通用要求见 [Skill 通用维护约定](README.md)。

## 能力定位

评估指定代码与当前项目文档的风险和重构机会，区分事实证据与建议收益。当前内容正确，也可能存在值得处理的维护成本；保持现状同样可以是合理结论。

维护时保留用户选择领域、可选预分析、默认只读和独立核实候选的边界。不要把评估自动变成修复，也不要要求先证明运行故障才能报告重构机会。

## 规则归属与引用

引用保持单向：入口可引用领域和公共资源，领域可引用公共资源；领域之间不互引，公共资源不反向引用领域。

- 所有检查都需要的执行约束留在入口，例如证据判定、只读范围和完成标准。
- 只影响一种检查视角的判断放入对应领域；先检查已有领域能否容纳，再决定是否新增。
- 确认多个领域实际共用同一判断标准后，再提取到 `references/` 并在使用处引用；入口导航或维护文档链接不算独立使用点。只服务一个领域的内容内联到该领域，暂无共享内容时不创建公共资源目录。
- few-shot 与对应规则放在一起，保留能区分应报告、应保留或证据不足的例子；不把示例另建为领域。

领域与公共资源的文件名用 kebab-case 英文，正文以中文主题为标题，说明范围、判断标准和边界。只写当前约定，不写历史沿革；借鉴其他 skill 的判断方法时，不引入其执行流程。

代码目录布局、规模参考及对应示例由架构领域维护，其他领域只沿相关线索核对，不额外执行完整架构检查。

项目的明确要求覆盖本 skill 的通用默认值，未规定的部分才采用默认规则。这一优先级适用于所有领域，不能仅在架构或代码组织中生效；现状描述与设计理由也不能被误当成强制要求。

各领域核对与目标相关的当前项目文档；完整的文档合并、表达与导航评估归文档领域。归档范围、代码与文档冲突时的判断按入口执行，不另立一套规则。

## 修改与验证

1. 读入口、拟修改领域及其公共资源，指出本次改变哪项判断或行为，检查是否已有规则表达同一意思。
2. 在所属位置修改；涉及归属调整时同步更新路径与读取条件，避免留下重复规则。新增领域应有独立视角、明确边界和少量有效示例。
3. 核对预分析、reviewer 和 verifier 能否通过所给文件引用找到适用规则，理解任务与范围。派发优先引用文件，由 subagent 自行读取；reviewer 的 prompt 按目标写入逐个阅读、场景推演、维护成本追踪、候选交接和完成条件，不维护固定模板或要求复制规则全文。
4. 用具体请求推演受影响分支，检查用户选区、交叉线索与报告结论是否仍符合范围。新增示例不能替代对实际目标的核实。
5. 按通用约定检查资源引用，再核对领域发现范围、元数据和改动 diff；运行 `rtk git diff --check`。验证说明区分静态检查、场景推演与实际执行，不能互相替代。

完成标准尤其要覆盖以下情况：

- 只有执行完成的领域才能作检查结论；超时、派发失败或未返回结果不能算作“没有 finding”。
- 阅读位置和核对路径应支持完成声明，局部抽查不能代替约定范围；跨模块、领域或文档主题的补漏与候选验证各有职责，均不替代未完成的领域检查。
- 独立 verifier 未完成时，候选仍是未验证项；主 agent 自查不能冒充独立验证。
- 事实成立但收益不足时，可以建议暂缓；测试通过也不能直接排除有证据的维护成本。
